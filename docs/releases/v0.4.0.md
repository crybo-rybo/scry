# Scry v0.4.0

Scry v0.4.0 is a consumer-experience release. v0.3.0 settled what the library is;
this one comes from integrating a real application — the pig-pen project — on top
of it and writing down every place the integration had to work around the API
rather than use it. A tool handler could not tell the model why it refused. A host
could not tell which round a tool call belonged to, or how much tool work a turn
did, without counting observations itself. A handler saw only its arguments, so
correlating tool work with a turn meant counting dispatches and hoping the count
matched. Nothing stood between the model's tool call and the handler that served
it, so a budget or a kill switch had to be re-implemented inside every handler.
Hitting `max_tool_rounds` failed the turn and rolled history back, even though the
tools that already ran had changed host state and could not be rolled back with
it. And testing any of it meant either a live provider or a hand-rolled transport
fake.

Each of those is now a small, additive piece of public surface:
`Error::model_message` and `scry::tool_error()`, round and call metadata on
`ToolCall` and `Completion`, `ToolCallContext` for handlers,
`TurnCallbacks::on_tool_request` with `Config::max_tool_calls_per_turn`,
`Config::tool_round_limit`, two reflection conveniences, and `scry::testing` —
the scripted transport Scry's own suites run on, published as a package
component. Nothing was removed or renamed. The breaks are the ones that come
with appending fields to public aggregates and adding an enumerator, plus one
overload-resolution ambiguity; they are listed below.

## Breaking changes

### Aggregate layouts changed

Appending a defaulted member to an aggregate does not break an existing
positional initializer: the omitted trailing field takes its default. Inserting
one in the middle does, and two public aggregates gained members mid-declaration:

- `Config` gains `max_tool_calls_per_turn` and `tool_round_limit` directly after
  `max_tool_rounds`, ahead of `tls_verify_peer`, `ca_bundle_path`, `proxy`, and
  `extra_headers`.
- `TurnCallbacks` gains `on_tool_request` between `on_text_delta` and
  `on_tool_call`.

A positional initializer or a structured binding that reaches past
`max_tool_rounds` or `on_text_delta` now names a different member and fails to
compile or changes meaning. Designated initializers keep working. `Error`,
`ToolCall`, and `Completion` only append members, so their positional
initializers still compile; structured bindings over them change arity. Every
one of these types changed layout, so binary consumers must be rebuilt.

```cpp
scry::Error error{
    .category = scry::ErrorCategory::tool,
    .message = "host-side diagnostic",
    .model_message = "text the model is allowed to see",
};
```

### `registry.add(definition, {})` is ambiguous

`ToolRegistry::add` now has a second overload taking a `ContextualToolHandler`.
The two are separated by the handler's arity alone, which works for any lambda or
callable of either shape but not for a braced empty initializer, which no longer
says which handler it is empty of. Spell the type:

```cpp
auto status = tools.add(definition, scry::ToolHandler{});
```

An empty handler of either shape is still rejected at registration, so this only
affects code that deliberately registers one — in practice, tests.

### Tool-error text the model sees has changed

Two fixed diagnostics are now derived from the schema and tool list the model was
already given, so a test that matches them exactly must be updated:

- An unknown tool was `model requested an unknown tool`. It now names the
  requested tool and the registered ones: `unknown tool "<name>"; registered
  tools: a, b, c`, or `unknown tool "<name>"; no tools are registered`.
- A reflected decode failure on an enum was `is not a declared enumerator`. It now
  appends the declared names: `is not a declared enumerator; must be one of:
  north, south, east, west`.

### `FinishReason::tool_round_limit`

`FinishReason` gains `tool_round_limit`. It is appended after `unknown`, so no
existing enumerator's underlying value shifts, but an exhaustive `switch` over
`FinishReason` now needs a case for it — under `-Wswitch` with warnings as errors,
that is a build failure rather than a silent fallthrough. A consumer that leaves
`Config::tool_round_limit` at its default never observes the value.

The same section of `<scry/events.hpp>` also writes down a contract the loop has
always enforced rather than changing one: `FinishReason::tool_use` is internal.
`validate_response` requires it exactly when a response carries tool calls, so
such a response starts another round or fails, and a `Completion` never carries
`tool_use`. Code that tested for it in a completion was testing for something that
could not happen.

### Header dependencies

`<scry/events.hpp>` now includes `<scry/tool_registry.hpp>` and
`<scry/message.hpp>`, because `ToolRequest` embeds a `ToolCallContext` and
`Completion::unexecuted_tool_calls` is a `std::vector<ToolCallBlock>`. Each public
header still compiles standalone. Consumers that include `<scry/scry.hpp>` see no
difference.

## New

### Model-visible tool errors

A handler can now tell the model why it refused. `Error::model_message` is an
opt-in field that dispatch forwards inside the result's `{"error": ...}` payload,
and `scry::tool_error(model_message, host_message)` builds one:

```cpp
return std::unexpected(scry::tool_error(
    "a wall blocks that direction; only north is open from the entrance hall",
    "player attempted a blocked move from the entrance hall"));
```

Only the first string reaches the model. `Error::message` and any exception text
stay on the host side, exactly as before, and a handler error that leaves
`model_message` empty behaves exactly as it did in v0.3.0. The text is bounded by
`ResourceLimits::max_tool_result_bytes`; one too large for the cap falls back to
Scry's fixed diagnostic. An empty `host_message` copies `model_message` into
`Error::message`, so a handler that wants one diagnostic writes it once.

Scry applies no redaction to `model_message` — the worker's API-key redaction runs
on attempt errors, not on tool results. A host that puts a secret in one has
published it.

Reflected decode failures fill `model_message` themselves, with the host message
minus its `reflected JSON at ` prefix: the JSON path of the offending value and
what the schema required there. Argument text that is not JSON at all reports
`tool arguments are not valid JSON`. Every word of it is derived from the schema
the model already received, so a model retrying an enum argument no longer has to
guess.

`examples/tool_policy.cpp` is a complete program in this shape.

### Turn metadata

`ToolCall` carries the one-based `round` it belongs to and its zero-based `index`
in that round's batch, in provider order. `Completion` carries
`tool_round_count` and `tool_call_count` for what the loop ran before the final
response; the call count includes unknown tools and calls whose handler failed.

The delivery ordering is now documented as a guarantee: text deltas of round N+1
are delivered only after every `on_tool_call` of round N, so a host can attribute
deltas to rounds by counting observations.

### Tool call context

`ToolRegistry::add(ToolDefinition, ContextualToolHandler)` is a second overload
whose handler receives a leading `ToolCallContext` — the `TurnId`, the
provider-assigned `call_id`, the registered `tool_name`, the one-based `round`,
and the zero-based `index` in that round's batch. These are the same values the
later `on_tool_call` observation reports.

Reflected handlers take the context the same way, as an optional leading
parameter:

```cpp
auto status = scry::reflection::add<ForecastArgs>(
    tools, {.name = "traced_forecast", .description = "Return the forecast"},
    [](const scry::ToolCallContext& context, ForecastArgs args) -> Forecast {
      log(context.turn_id, context.round, context.call_id);
      return lookup_forecast(std::move(args));
    });
```

`ToolHandlerFor` accepts either arity and prefers the contextual form; a trailing
context is a compile error. The context is borrowed — both string views point into
the call block being dispatched and die with the invocation, so a handler that
keeps either must copy the text. Registrations store one handler shape internally,
so the two paths export an identical tool contract and differ in nothing the model
can see.

### Tool admission and a per-turn call limit

Two gates now sit in front of every handler, in a fixed order.

`Config::max_tool_calls_per_turn` bounds the calls one turn may dispatch across
every round. `max_tool_rounds` could never do that on its own, because one
response carries a whole batch. Unset means unlimited; zero is rejected as
`invalid_config` by `Harness::create()` and `Harness::validate()`.

Then `TurnCallbacks::on_tool_request`, the host's own policy. It receives a
`ToolRequest` naming the call and its canonical arguments and answers with an
empty optional to admit it or a `ToolRejection` carrying the text the model should
see:

```cpp
.on_tool_request = [](const scry::ToolRequest& request)
    -> std::optional<scry::ToolRejection> {
  if (allowed(request.context.tool_name)) { return std::nullopt; }
  return scry::ToolRejection{.model_message = "that tool is not available here"};
},
```

A refusal is an answer, not a failure. The model gets `{"error": message}` flagged
as a tool error, the same block reaches `on_tool_call` with `is_error`, and the
result is posted to the worker like any other, so the turn completes and commits.
`Completion::rejected_tool_call_count` counts the refusals; each is also counted
by `tool_call_count`. A refused call runs no handler and so can have no side
effect.

Every call that reaches the route spends the limit, including one naming a tool
nobody registered: the model spent the budget by asking. An unknown tool is still
refused by dispatch with its own message and never reaches the hook, because there
is no handler for the host to admit. A hook that throws is treated exactly like a
handler that throws — the call is refused with the fixed text and the turn carries
on — and one that calls `disconnect()` is deferred by the same invocation guard as
every other callback and suppresses its own observation.

This is also the supported way to stop dispatching mid-turn. Cancelling from a
handler discards the pending transcript, including the results the executed
tools produced, but not their side effects: a handler's host-side mutations
remain, and reconciling them is the host's job. A flag the hook consults instead
lets the turn finish and commit, while every later call is refused with a reason
the model can act on.

### A round-limit policy that completes instead of failing

`Config::tool_round_limit` chooses what a response requesting tools past
`max_tool_rounds` does. `ToolRoundLimitPolicy::fail` is the default and the
v0.3.0 behavior: the turn fails with `max_tool_rounds` and commits nothing.
`ToolRoundLimitPolicy::complete` stops the turn instead of failing it — it commits
the rounds that ran plus the final response's text, drops that response's
tool-call blocks into `Completion::unexecuted_tool_calls`, and reports
`FinishReason::tool_round_limit`.

That keeps host state and history in agreement: the dropped calls never ran, so
nothing they would have changed happened, and the host learns what the model asked
for and can put it in the next `send()`. The dropped calls are reserved against
the Conversation byte limit during the turn exactly as the round they replace
would have been, so a list that does not fit fails the turn with `resource_limit`
just as an oversized tool round does; they are never charged to the queued-event
limit and never committed to history. Those calls count in neither
`tool_call_count` nor `rejected_tool_call_count`: the model asked and was not
answered.

A calls-only stopping response leaves nothing to commit, so the transcript ends
with the previous round's tool-result user message rather than gaining an empty
assistant message. Because history can now end on a user message, the Anthropic
adapter merges consecutive same-role messages into one message whose content array
concatenates their blocks — the Messages API takes one message per role turn. The
OpenAI adapter already emits tool results as their own messages and is unchanged.

### Reflection ergonomics

`scry::reflection::schema_v<Value>` generalizes the existing generator from
argument aggregates to the whole `SupportedValue` matrix, so a host can export the
schema of a handler result type and publish a full tool contract next to
`ToolRegistry::to_json()`. Scry still sends only `input_schema_v<Args>` to a
provider; `input_schema_v` keeps its spelling and is now an alias of `schema_v`.
The canonical example gained a `--result-schema` flag that prints one.

`scry::reflection::description_of<View>()` builds the same annotation payload as
the literal `description{...}` form from a `std::string_view` with static storage
duration, so parameter text can live in one catalog instead of in literals spread
across aggregates. The copy runs inside `description<Size>` through a private
tagged constructor, so the annotation type is unchanged and the schema generator's
detection is untouched.

### `scry::testing`

`scry::testing` is a second static library installed as the package component
`testing`, built unless `SCRY_BUILD_TESTING_SUPPORT` is off. It publishes the
scripted transport, the injected-component Harness builder, and the per-dialect
stream builders that were previously private to Scry's own suites.

```cmake
find_package(scry 0.4.0 CONFIG REQUIRED COMPONENTS testing)
target_link_libraries(my_tests PRIVATE scry::scry scry::testing)
```

```cpp
scry::testing::ScriptedTransport transport;
transport.enqueue({.body_chunks = {scry::testing::anthropic_text_stream("hi")}});
auto harness = scry::testing::create_harness(my_config(), transport);
```

`ScriptedTransport` is a queue of scripted responses that also records what the
runtime sent; `requests()` returns the bytes Scry actually put on the wire, and
the handle stays valid for inspection after `create_harness`, because the script
lives in a shared implementation and the Harness is handed a thin forwarder over
it. `ScriptedResponse` can also script a transfer that fails, so retry paths are
reachable, or one that blocks until `release()`, so cancellation mid-transfer is.
`<scry/testing/streams.hpp>` builds the response bodies each dialect decodes:
`anthropic_text_stream`, `anthropic_tool_stream`, `openai_text_stream`,
`openai_tool_stream`, and `openai_error_body`.

It substitutes for the HTTP transfer and nothing else. A scripted turn still runs
the real worker, the real provider request encoder and stream decoder, real retry
scheduling, real tool dispatch, transactional history, and the real pump, so a
test written against it fails when Scry's behavior changes rather than when a
mock's expectations drift. It does not exercise libcurl, TLS, or any timeout curl
enforces; those stay covered by the loopback transport and integration suites.
Retry waits are real time bounded by the `Config`'s retry policy, so a test that
scripts a retried failure should shrink `initial_backoff` and `max_backoff` rather
than pay production backoff. Retry jitter is seeded rather than randomized, so a
scripted retry sequence is reproducible.

Scry's own `tests/support/harness_test_support.hpp` now forwards to the public
builders, so the shipped component is what the suites exercise.
`examples/testing_scripted.cpp` is a complete framework-free test in this shape,
and the package consumer drives a whole scripted turn from the installed package.
`-DSCRY_BUILD_TESTING_SUPPORT=OFF` builds and installs none of it, in which case a
consumer must not request the component.

## Migration

A v0.3.0 consumer that uses none of the above needs only a rebuild and, if it
switches exhaustively on `FinishReason`, one new case.

**A handler that wants the model to see its refusal.** Before, the model received
a fixed string and the reason stayed in the host's log:

```cpp
return std::unexpected(scry::Error{
    .category = scry::ErrorCategory::tool,
    .message = "player attempted a blocked move",
});
```

After:

```cpp
return std::unexpected(scry::tool_error(
    "a wall blocks that direction; only north is open",
    "player attempted a blocked move"));
```

**Registering a handler that needs its call's identity.** Before, the handler took
only its arguments and the host counted dispatches to correlate them:

```cpp
auto status = scry::reflection::add<MoveArguments>(tools, metadata,
    [](MoveArguments args) -> MoveResult { return move(args); });
```

After:

```cpp
auto status = scry::reflection::add<MoveArguments>(tools, metadata,
    [](const scry::ToolCallContext& context, MoveArguments args) -> MoveResult {
      trace(context.turn_id, context.round, context.index);
      return move(args);
    });
```

The explicit-schema path takes the same shape through the new
`ContextualToolHandler` overload of `ToolRegistry::add`.

**Bounding tool calls per turn.** Before, `max_tool_rounds` was the only bound and
it counted rounds, not calls:

```cpp
scry::Config config{.model = "...", .max_tool_rounds = 8};
```

After:

```cpp
scry::Config config{
    .model = "...",
    .max_tool_rounds = 8,
    .max_tool_calls_per_turn = 32,
};
```

**Stopping further tool work without losing the turn.** Before, the only lever was
`cancel()` from inside a handler, which discarded the turn's transcript while the
side effects of the tools that had already run stayed behind for the host to
reconcile. After:

```cpp
.on_tool_request = [&app](const scry::ToolRequest&)
    -> std::optional<scry::ToolRejection> {
  if (!app.tools_enabled) {
    return scry::ToolRejection{
        .model_message = "tools are unavailable; answer with what you have",
    };
  }
  return std::nullopt;
},
```

**Completing at the round limit instead of failing.** Before, a turn that hit
`max_tool_rounds` failed with `ErrorCategory::max_tool_rounds` and committed
nothing. After:

```cpp
scry::Config config{
    .model = "...",
    .tool_round_limit = scry::ToolRoundLimitPolicy::complete,
};

// in on_finished, on success:
if (completion.finish_reason == scry::FinishReason::tool_round_limit) {
  report(completion.unexecuted_tool_calls.size());
}
```

**Testing against the scripted transport.** Before, a downstream test needed a
live provider or its own transport fake. After:

```cmake
find_package(scry 0.4.0 CONFIG REQUIRED COMPONENTS testing)
target_link_libraries(my_tests PRIVATE scry::scry scry::testing)
```

```cpp
#include <scry/testing/scripted_transport.hpp>
#include <scry/testing/streams.hpp>

scry::testing::ScriptedTransport transport;
transport.enqueue({.body_chunks = {scry::testing::openai_text_stream("hello")}});
auto harness = scry::testing::create_harness(config, transport, std::move(tools));
```

**Anywhere a positional aggregate initializer or structured binding reaches into
`Config` past `max_tool_rounds` or into `TurnCallbacks` past `on_text_delta`.**
Switch to designated initializers in declaration order, as v0.3.0 already
recommended for `Error`, and re-count structured bindings over any of the
changed aggregates.

**Anywhere `registry.add(definition, {})` appears.** Write
`registry.add(definition, scry::ToolHandler{})`.

## Validation

Every change in this release landed as its own pull request, each gated the same
way.

Locally, each branch ran `./scripts/preflight.sh` before it was opened: the core
gate (`git diff --check`, lizard at cyclomatic complexity 15 and 6 arguments,
`scripts/format.sh --check`, the `ci` build with warnings as errors, the complete
`ctest` suite, a staged install, and the installed-package consumer), the
clang-tidy leg, ASan with non-recovering UBSan, TSan, and the fuzz corpus replay.
Only the Doxygen leg was skipped, because the development host has no Doxygen;
hosted CI is authoritative for it.

Hosted CI ran the same scripts under `scripts/` on every pull request, on GCC 16
for Linux and macOS: the core gate on both, the ASan+UBSan and TSan legs, the
clang-tooling build that proves `src/` stays free of reflection syntax, the fuzz
targets replayed against their checked-in seed corpora, and the API-site build
with the pinned clang-format 18 check.

Behavior changes came with tests first and a `docs/architecture.md` update;
public API additions came with a compiling example and `static_assert`s in
`tests/public_api_contract.cpp`. The new `testing.` ctest suite exercises the
shipped `scry::testing` component, Scry's own support header forwards to it, and
the package consumer links the component and drives a whole scripted turn from the
installed package.

Scry remains pre-1.0: API, ABI, and persisted conversation formats may change
between releases.

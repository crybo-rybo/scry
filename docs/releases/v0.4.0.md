# Scry v0.4.0

Scry v0.4.0 is a release for the consumer experience. v0.3.0 defined what the
library is. This release comes from the integration of a real application, the
pig-pen project, on top of the library. The work recorded each place where the
integration used a workaround instead of the API.

These were the problems:

- A tool handler did not have a way to tell the model why it refused.
- A host had to count observations itself. Without this count, it did not know
  the round of a tool call or the quantity of tool work in a turn.
- A handler got only its arguments. To correlate tool work with a turn, the host
  counted dispatches and hoped that the count was correct.
- Nothing was between the tool call of the model and the handler that served it.
  Thus, it was necessary to implement a budget or a kill switch again inside
  each handler.
- When a turn got to `max_tool_rounds`, the turn failed and history rolled back.
  But the tools that ran before that changed the host state, and the rollback
  did not undo those changes.
- To test any of this, it was necessary to use a live provider or a transport
  fake that you wrote yourself.

This release adds a small part of public API for each of these problems. Each
part is an addition:

- `Error::model_message` and `scry::tool_error()`
- round and call metadata on `ToolCall` and `Completion`
- `ToolCallContext` for handlers
- `TurnCallbacks::on_tool_request` with `Config::max_tool_calls_per_turn`
- `Config::tool_round_limit`
- two reflection conveniences
- `scry::testing`, the scripted transport that the Scry test suites use, which
  this release publishes as a package component.

This release does not remove or rename anything. The breaking changes come from
new fields in public aggregates, a new enumerator, and one ambiguity in overload
resolution. The sections that follow list them.

## Breaking changes

### Aggregate layouts changed

If you add a member with a default value at the end of an aggregate, an existing
positional initializer does not break. The initializer omits the trailing field,
so that field gets its default value. If you add a member in the middle, the
initializer breaks. Two public aggregates got new members in the middle of the
declaration:

- `Config` gets `max_tool_calls_per_turn` and `tool_round_limit` immediately
  after `max_tool_rounds`, before `tls_verify_peer`, `ca_bundle_path`, `proxy`,
  and `extra_headers`.
- `TurnCallbacks` gets `on_tool_request` between `on_text_delta` and
  `on_tool_call`.

Some positional initializers and structured bindings go past `max_tool_rounds`
or `on_text_delta`. Such an initializer or binding now names a different member.
Thus, it does not compile, or its meaning changes. Designated initializers
continue to work. `Error`, `ToolCall`, and `Completion` only add members at the
end. Thus, their positional initializers continue to compile.

Structured bindings over these three types change arity. All of the types in
this section have a new layout, so you must rebuild binary consumers.

```cpp
scry::Error error{
    .category = scry::ErrorCategory::tool,
    .message = "host-side diagnostic",
    .model_message = "text the model is allowed to see",
};
```

### `registry.add(definition, {})` is ambiguous

`ToolRegistry::add` now has a second overload that takes a
`ContextualToolHandler`. Only the arity of the handler selects one of the two
overloads. This works for all lambdas and callables of the two shapes. It does
not work for an empty braced initializer, because that initializer does not show
which handler type it is. Write the type explicitly:

```cpp
auto status = tools.add(definition, scry::ToolHandler{});
```

Registration continues to reject an empty handler of the two shapes. Thus, this
change affects only code that registers an empty handler intentionally. In
practice, only tests do this.

### Changes to the tool-error text that the model sees

Two fixed diagnostics now come from the schema and the tool list that the model
already got. If a test compares these diagnostics exactly, update the test:

- For an unknown tool, the old text was `model requested an unknown tool`. The
  new text gives the name of the requested tool and the names of the registered
  tools: `unknown tool "<name>"; registered tools: a, b, c`, or
  `unknown tool "<name>"; no tools are registered`.
- For a reflected decode failure on an enum, the old text was
  `is not a declared enumerator`. The new text adds the declared names at the
  end: `is not a declared enumerator; must be one of:
  north, south, east, west`.

### `FinishReason::tool_round_limit`

`FinishReason` gets the new enumerator `tool_round_limit`. It comes after
`unknown`, so the underlying values of the existing enumerators do not change.
But an exhaustive `switch` over `FinishReason` now must have a case for it. With
`-Wswitch` and warnings as errors, a missing case causes a build failure, not a
silent fallthrough. If a consumer keeps the default value of
`Config::tool_round_limit`, it never sees this value.

The same section of `<scry/events.hpp>` also documents a contract. This release
does not change the contract, because the loop always enforced it. The contract
is that `FinishReason::tool_use` is internal. `validate_response` requires
`tool_use` when a response carries tool calls, and only then. Thus, such a
response starts another round or fails, and a `Completion` never carries
`tool_use`. Code that tested for `tool_use` in a completion tested for an
impossible condition.

### Header dependencies

`<scry/events.hpp>` now includes `<scry/tool_registry.hpp>` and
`<scry/message.hpp>`. The reason is that `ToolRequest` embeds a
`ToolCallContext`, and `Completion::unexecuted_tool_calls` is a
`std::vector<ToolCallBlock>`. Each public header continues to compile
standalone. Consumers that include `<scry/scry.hpp>` see no difference.

## New

### Model-visible tool errors

A handler can now tell the model why it refused. `Error::model_message` is an
opt-in field. Dispatch sends it to the model inside the `{"error": ...}` payload
of the result. `scry::tool_error(model_message, host_message)` makes an `Error`
with this field:

```cpp
return std::unexpected(scry::tool_error(
    "a wall blocks that direction; only north is open from the entrance hall",
    "player attempted a blocked move from the entrance hall"));
```

Only the first string gets to the model. `Error::message` and all exception text
stay on the host side, the same as before. If a handler error has an empty
`model_message`, it behaves exactly as in v0.3.0.
`ResourceLimits::max_tool_result_bytes` sets the maximum size of the text. If
the text is larger than this limit, Scry uses its fixed diagnostic instead.

If `host_message` is empty, `scry::tool_error()` copies `model_message` into
`Error::message`. Thus, a handler that wants one diagnostic writes it only once.

Scry does not redact `model_message`. The worker redacts API keys in attempt
errors, but not in tool results. If a host puts a secret in `model_message`, the
host publishes that secret.

For a reflected decode failure, Scry fills `model_message` itself. The text is
the host message without its `reflected JSON at ` prefix. It gives the JSON path
of the incorrect value and what the schema required at that path. If the
argument text is not JSON, the message is `tool arguments are not valid JSON`.
All of this text comes from the schema that the model already got. Thus, when a
model retries an enum argument, it does not have to guess.

`examples/tool_policy.cpp` is a complete program in this form.

### Turn metadata

`ToolCall` carries two new values. `round` is the one-based number of the round
that the call belongs to. `index` is the zero-based position of the call in the
batch of that round, in provider order.

`Completion` carries `tool_round_count` and `tool_call_count`. These values
count what the loop ran before the final response. The call count includes calls
to unknown tools and calls with a handler that failed.

The documentation now guarantees the delivery order. Scry delivers the text
deltas of round N+1 only after each `on_tool_call` of round N. Thus, a host can
count observations to find the round of each delta.

### Tool call context

`ToolRegistry::add(ToolDefinition, ContextualToolHandler)` is a second overload.
Its handler gets a `ToolCallContext` as the first parameter. The context has
these values:

- the `TurnId`
- the `call_id` that the provider assigns
- the registered `tool_name`
- the one-based `round`
- the zero-based `index` in the batch of that round.

These values are the same as the values that the later `on_tool_call`
observation reports.

Reflected handlers get the context in the same way, as an optional first
parameter:

```cpp
auto status = scry::reflection::add<ForecastArgs>(
    tools, {.name = "traced_forecast", .description = "Return the forecast"},
    [](const scry::ToolCallContext& context, ForecastArgs args) -> Forecast {
      log(context.turn_id, context.round, context.call_id);
      return lookup_forecast(std::move(args));
    });
```

`ToolHandlerFor` accepts the two arities and prefers the contextual form. If the
context comes after the arguments, a compile error occurs. The context is
borrowed. Its two string views point into the call block that Scry dispatches,
and they become invalid when the invocation ends. If a handler keeps one of these
views, it must copy the text.

Internally, all registrations store one handler shape. Thus, the two paths export
the same tool contract. The model cannot see a difference between them.

### Tool admission and a per-turn call limit

Two gates are now in front of each handler, in a fixed order.

The first gate is `Config::max_tool_calls_per_turn`. It sets the maximum number
of calls that one turn can dispatch, across all rounds. `max_tool_rounds` alone
cannot do this, because one response carries a full batch. If the value is not
set, there is no limit. `Harness::create()` and `Harness::validate()` reject zero
as `invalid_config`.

The second gate is `TurnCallbacks::on_tool_request`, the policy of the host. It
gets a `ToolRequest` that identifies the call and its canonical arguments. To
admit the call, it returns an empty optional. To refuse the call, it returns a
`ToolRejection` with the text for the model:

```cpp
.on_tool_request = [](const scry::ToolRequest& request)
    -> std::optional<scry::ToolRejection> {
  if (allowed(request.context.tool_name)) { return std::nullopt; }
  return scry::ToolRejection{.model_message = "that tool is not available here"};
},
```

A refusal is an answer, not a failure. The model gets `{"error": message}` as a
tool error. The same block goes to `on_tool_call` with `is_error`. Scry posts the
result to the worker the same as all other results, so the turn completes and
commits. `Completion::rejected_tool_call_count` counts the refusals, and
`tool_call_count` also counts each refusal. A refused call runs no handler, so it
cannot have a side effect.

Each call that gets to the route uses part of the limit. This includes a call to
a tool that is not registered, because the model used the budget when it asked.
Dispatch continues to refuse an unknown tool with its own message. That call
never gets to the hook, because there is no handler for the host to admit.

Scry treats a hook that throws exactly like a handler that throws. Scry refuses
the call with the fixed text, and the turn continues. If a hook calls
`disconnect()`, the same invocation guard as for all other callbacks defers the
disconnect. The disconnect also suppresses the observation of that call.

The hook is also the supported way to stop dispatch in the middle of a turn. If
you cancel from a handler, Scry discards the pending transcript. This includes
the results of the tools that ran, but not their side effects. The host-side
changes of a handler stay, and the host must reconcile them. Instead, the hook
can read a flag. Then the turn finishes and commits, and each subsequent call
gets a refusal with a reason that the model can use.

### A round-limit policy that completes and does not fail

`Config::tool_round_limit` selects what occurs when a response requests tools
beyond `max_tool_rounds`. `ToolRoundLimitPolicy::fail` is the default, and it is
the v0.3.0 behavior. The turn fails with `max_tool_rounds` and commits nothing.
`ToolRoundLimitPolicy::complete` stops the turn, but the turn does not fail. This
policy does these steps:

- It commits the rounds that ran and the text of the final response.
- It moves the tool-call blocks of that response into
  `Completion::unexecuted_tool_calls`.
- It reports `FinishReason::tool_round_limit`.

This keeps the host state and the history in agreement. The removed calls never
ran, so they changed nothing. The host knows what the model asked for, and it can
put this request in the next `send()`.

During the turn, Scry reserves space for the removed calls in the Conversation
byte limit. It does this exactly as for the round that they replace. Thus, if
the list does not fit, the turn fails with `resource_limit`, the same as for a
tool round that is too large. Scry never charges these calls to the queued-event
limit and never commits them to history. `tool_call_count` and
`rejected_tool_call_count` do not count these calls, because the model asked and
got no answer.

If the response that stops the turn has only calls, there is nothing to commit.
Thus, the transcript ends with the tool-result user message of the previous
round, and Scry does not add an empty assistant message. Because the history can
now end with a user message, the Anthropic adapter merges consecutive messages
with the same role into one message. The content array of that message
concatenates their blocks. The reason is that the Messages API accepts one
message for each role turn. The OpenAI adapter does not change, because it
already sends tool results as their own messages.

### Reflection ergonomics

`scry::reflection::schema_v<Value>` extends the existing generator. Before, the
generator applied only to argument aggregates. Now it applies to the full
`SupportedValue` matrix. Thus, a host can export the schema of a handler result
type and publish a full tool contract together with `ToolRegistry::to_json()`.
Scry continues to send only `input_schema_v<Args>` to a provider. The name
`input_schema_v` does not change, and it is now an alias of `schema_v`.

The canonical example got a new `--result-schema` flag that prints such a
schema.

`scry::reflection::description_of<View>()` makes the same annotation payload as
the literal `description{...}` form. It makes this payload from a
`std::string_view` with static storage duration. Thus, parameter text can be in
one catalog, not in literals in many different aggregates. The copy occurs
inside `description<Size>`, through a private tagged constructor. Thus, the
annotation type does not change, and the detection in the schema generator does
not change.

### `scry::testing`

`scry::testing` is a second static library. It installs as the package component
`testing`. The build includes it unless `SCRY_BUILD_TESTING_SUPPORT` is off. It
publishes these items, which before were private to the Scry test suites:

- the scripted transport
- the Harness builder for injected components
- the stream builders for each dialect.

```cmake
find_package(scry 0.4.0 CONFIG REQUIRED COMPONENTS testing)
target_link_libraries(my_tests PRIVATE scry::scry scry::testing)
```

```cpp
scry::testing::ScriptedTransport transport;
transport.enqueue({.body_chunks = {scry::testing::anthropic_text_stream("hi")}});
auto harness = scry::testing::create_harness(my_config(), transport);
```

`ScriptedTransport` is a queue of scripted responses. It also records what the
runtime sent. `requests()` returns the bytes that Scry actually put on the wire.
After `create_harness`, the handle stays valid, so you can examine it. The reason
is that the script is in a shared implementation, and the Harness gets only a
thin forwarder to it.

`ScriptedResponse` can also script a transfer that fails, so a test can get to
the retry paths. It can also script a transfer that blocks until `release()`, so
a test can cancel in the middle of a transfer. `<scry/testing/streams.hpp>`
builds the response bodies that each dialect decodes: `anthropic_text_stream`,
`anthropic_tool_stream`, `openai_text_stream`, `openai_tool_stream`, and
`openai_error_body`.

It replaces only the HTTP transfer. A scripted turn continues to run these real
components:

- the worker
- the provider request encoder and stream decoder
- retry scheduling
- tool dispatch
- transactional history
- the pump.

Thus, a test that uses it fails when the behavior of Scry changes. It does not
fail when the expectations of a mock become incorrect. It does not test libcurl,
TLS, or the timeouts that curl enforces. The loopback transport and the
integration suites continue to cover those.

Retry waits use real time, and the retry policy of the `Config` sets their
limits. If a test scripts a failure that Scry retries, make `initial_backoff`
and `max_backoff` smaller. Then the test does not wait for the production
backoff. Retry jitter uses a seed, not random values. Thus, a scripted retry
sequence is reproducible.

The Scry file `tests/support/harness_test_support.hpp` now forwards to the
public builders. Thus, the suites test the shipped component.
`examples/testing_scripted.cpp` is a complete test in this form, and it uses no
framework. The package consumer runs a full scripted turn from the installed
package. With `-DSCRY_BUILD_TESTING_SUPPORT=OFF`, the build does not build or
install any of it. In that configuration, a consumer must not request the
component.

## Migration

If a v0.3.0 consumer uses none of these features, rebuild it. If it has an
exhaustive `switch` on `FinishReason`, add one case.

**A handler that wants the model to see its refusal.** Before, the model got a
fixed string, and the reason stayed in the log of the host:

```cpp
return std::unexpected(scry::Error{
    .category = scry::ErrorCategory::tool,
    .message = "player attempted a blocked move",
});
```

After:

```cpp
return std::unexpected(scry::tool_error(
    "a wall blocks that direction; only north is open",
    "player attempted a blocked move"));
```

**Register a handler that needs the identity of its call.** Before, the handler
got only its arguments. To correlate the calls with the turn, the host counted
dispatches:

```cpp
auto status = scry::reflection::add<MoveArguments>(tools, metadata,
    [](MoveArguments args) -> MoveResult { return move(args); });
```

After:

```cpp
auto status = scry::reflection::add<MoveArguments>(tools, metadata,
    [](const scry::ToolCallContext& context, MoveArguments args) -> MoveResult {
      trace(context.turn_id, context.round, context.index);
      return move(args);
    });
```

For the explicit-schema path, use the new `ContextualToolHandler` overload of
`ToolRegistry::add` in the same way.

**Limit the tool calls for each turn.** Before, `max_tool_rounds` was the only
limit, and it counted rounds, not calls:

```cpp
scry::Config config{.model = "...", .max_tool_rounds = 8};
```

After:

```cpp
scry::Config config{
    .model = "...",
    .max_tool_rounds = 8,
    .max_tool_calls_per_turn = 32,
};
```

**Stop more tool work and keep the turn.** Before, the only method was `cancel()`
from inside a handler. It discarded the transcript of the turn. But the side
effects of the tools that already ran stayed for the host to reconcile. After:

```cpp
.on_tool_request = [&app](const scry::ToolRequest&)
    -> std::optional<scry::ToolRejection> {
  if (!app.tools_enabled) {
    return scry::ToolRejection{
        .model_message = "tools are unavailable; answer with what you have",
    };
  }
  return std::nullopt;
},
```

**Complete the turn at the round limit, and do not fail it.** Before, when a
turn got to `max_tool_rounds`, it failed with `ErrorCategory::max_tool_rounds`
and committed nothing. After:

```cpp
scry::Config config{
    .model = "...",
    .tool_round_limit = scry::ToolRoundLimitPolicy::complete,
};

// in on_finished, on success:
if (completion.finish_reason == scry::FinishReason::tool_round_limit) {
  report(completion.unexecuted_tool_calls.size());
}
```

**Test against the scripted transport.** Before, a downstream test needed a live
provider or its own transport fake. After:

```cmake
find_package(scry 0.4.0 CONFIG REQUIRED COMPONENTS testing)
target_link_libraries(my_tests PRIVATE scry::scry scry::testing)
```

```cpp
#include <scry/testing/scripted_transport.hpp>
#include <scry/testing/streams.hpp>

scry::testing::ScriptedTransport transport;
transport.enqueue({.body_chunks = {scry::testing::openai_text_stream("hello")}});
auto harness = scry::testing::create_harness(config, transport, std::move(tools));
```

**A positional aggregate initializer or structured binding that goes past
`max_tool_rounds` in `Config` or past `on_text_delta` in `TurnCallbacks`.** Use
designated initializers in declaration order. v0.3.0 already recommended this
for `Error`. Count again the structured bindings over all aggregates that
changed.

**Each use of `registry.add(definition, {})`.** Write
`registry.add(definition, scry::ToolHandler{})`.

## Validation

Each change in this release landed as a separate pull request. The same gates
applied to each pull request.

Each branch ran `./scripts/preflight.sh` locally before its pull request opened.
The script ran these legs:

- the core gate: `git diff --check`, lizard at cyclomatic complexity 15 and 6
  arguments, `scripts/format.sh --check`, the `ci` build with warnings as
  errors, the complete `ctest` suite, a staged install, and the
  installed-package consumer
- the clang-tidy leg
- ASan with non-recovering UBSan
- TSan
- the fuzz corpus replay.

Only the Doxygen leg did not run, because the development host has no Doxygen.
Hosted CI is the authority for that leg.

Hosted CI ran the same scripts in `scripts/` on each pull request, with GCC 16 on
Linux and macOS. It ran these legs:

- the core gate on the two platforms
- the ASan+UBSan and TSan legs
- the clang-tooling build, which proves that `src/` stays free of reflection
  syntax
- the fuzz targets, which replayed their checked-in seed corpora
- the API-site build with the pinned clang-format 18 check.

Each behavior change landed with tests first and an update to
`docs/architecture.md`. Each public API addition landed with a compiling example
and `static_assert`s in `tests/public_api_contract.cpp`. The new `testing.` ctest
suite tests the shipped `scry::testing` component. The support header of Scry
forwards to this component. The package consumer links the component and runs a
full scripted turn from the installed package.

Scry is still pre-1.0. The API, the ABI, and the persisted conversation formats
can change between releases.

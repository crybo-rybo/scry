# Scry v0.5.0

Scry v0.5.0 adds an optional sampling seed for OpenAI-compatible servers, fixes
two bugs (control characters producing invalid JSON, and reflected handlers
returning `Result<const T>` failing to compile), and closes out the remaining
tool-boundary issues from the pig-pen integration with clearer documentation.
Underneath, it is a large simplification pass: about 2,500 fewer lines across
the library, tests, and build, with no change to a documented guarantee beyond
the few behavior details listed below.

It is a minor release because it removes three helpers from the public
`scry::testing` streams header and changes the layout of several public types,
so binary consumers must be rebuilt.

## Breaking changes

### Three `scry::testing` stream helpers removed

`<scry/testing/streams.hpp>` no longer declares these functions in
`scry::testing`. Nothing in Scry used them outside the builders themselves.
([#107](https://github.com/crybo-rybo/scry/pull/107))

| Removed | Use instead |
|---|---|
| `json_string(text)` | `scry::escape_json_string(text)` from `<scry/json.hpp>`, which it wrapped unchanged |
| `anthropic_tool_block_events(index, block)` | `anthropic_tool_stream({...})` for a complete body |
| `openai_tool_call_entry(index, block)` | `openai_tool_stream({...})` for a complete body |

The frame pieces the builders share now live in `scry::testing::stream_frames`,
which is documented as internal and may change without notice.

### Layout changes

- `SamplingConfig` appends `seed`, so `Config` changes size. Positional and
  designated initializers keep compiling; structured bindings over
  `SamplingConfig` change arity.
- `Conversation` now holds its state through a `std::shared_ptr` (previously a
  `std::unique_ptr`), and `JsonView` holds one aliasing `std::shared_ptr`
  instead of a document pointer plus a node pointer. Neither change is visible
  in the API.

Every one of these types is carried by value or embedded in public types, so
binary consumers must be rebuilt.

## New

### Sampling seed

`SamplingConfig::seed` is an optional `std::uint32_t`. The OpenAI-compatible
dialect sends it as the Chat Completions `seed` field when set and omits it when
unset, so existing requests are unchanged. The same value goes with every
request of a turn, retries and tool rounds included.

The Anthropic Messages API has no seed, so the Anthropic dialect rejects a set
value during validation, the way it rejects disabled reasoning, rather than drop
it and let a host believe its runs were seeded.

Scry passes the seed through and promises nothing about repeatability. Whether
the same seed, model, prompt, and sampling values reproduce an output is up to
the server, is best-effort there, and does not carry across models, servers, or
server versions. The field is 32 bits so that every value fits the seed range
OpenAI-compatible servers accept and survives JSON parsers that read numbers as
doubles.

```cpp
auto harness = scry::Harness::create({
    .base_url = "http://127.0.0.1:11434/v1",
    .model = "qwen3:8b",
    .dialect = scry::ProviderDialect::openai_compatible,
    .sampling = {.temperature = 0.8, .seed = 42},
});
```

The new `examples/seeded_trials.cpp` runs one prompt several times against a
local model with a fixed seed and reports whether the answers matched.
([#42](https://github.com/crybo-rybo/scry/issues/42),
[#112](https://github.com/crybo-rybo/scry/pull/112))

## Fixes

- **JSON control characters.** Every JSON write now escapes a control
  character that has no short escape (anything other than `\b`, `\f`, `\n`,
  `\r`, and `\t`) as `\u00XX`. Previously, tool arguments, text, or object keys
  containing a byte such as `\x01` or an ANSI escape were written as invalid
  JSON: a provider request could be rejected, and `Conversation::to_json()`
  could fail on a history that `Conversation::from_json()` had just accepted.
  Found by the scheduled conversation fuzzer; the crashing input is now a
  regression test and part of the fuzz corpus.
  ([#107](https://github.com/crybo-rybo/scry/pull/107),
  [#108](https://github.com/crybo-rybo/scry/issues/108))
- **`Result<const T>` reflected handlers.** A reflected handler returning
  `scry::Result<const T>` satisfied `ToolHandlerFor` but failed to compile
  inside the library. It now registers and encodes its value.
  ([#107](https://github.com/crybo-rybo/scry/pull/107))

## Behavior details

- **SSE:** a blank line ended by a lone CR now dispatches its event in the chunk
  that carries it, instead of waiting for the next byte.
- **`Conversation::from_json` diagnostics:** error messages now name the
  specific problem instead of `invalid prompt or messages`. The category is
  unchanged.
- **OpenAI stream errors:** an error `type` or `code` literally equal to
  `unknown_error` is now reported as that token instead of being treated as
  absent.
  ([#107](https://github.com/crybo-rybo/scry/pull/107))

## Documentation

- The `ToolHandler` comment and `docs/architecture.md` now say plainly what
  argument validation covers: Scry checks that tool arguments parse into a JSON
  object, not that they match the registered schema. The explicit-schema
  handler owns that check and should reject with `scry::tool_error()` so the
  model learns what to correct. The canonical example's `echo` handler now does
  this; it previously rejected with a plain `scry::Error`, so the model saw only
  `tool handler returned an error`.
  ([#39](https://github.com/crybo-rybo/scry/issues/39),
  [#112](https://github.com/crybo-rybo/scry/pull/112))
- `Error::model_message` and `docs/architecture.md` previously said an oversized
  `model_message` falls back to Scry's fixed diagnostic. It is replaced by the
  generic `tool execution failed`, which is what the code has always done.
- The README now leads with what Scry does, then requirements and installation.
  ([#106](https://github.com/crybo-rybo/scry/pull/106))
- The README and contributing guide now state the real CMake requirement:
  3.31, because the Glaze revision Scry fetches requires it. Scry's own build
  files still accept 3.28 when CMake finds a packaged Glaze. The Linux setup no
  longer installs Ubuntu 24.04's CMake 3.28, which the fetched Glaze rejects.
  The requirement is unchanged since v0.4.1, whose notes gave 3.28.

## Build and contributor tooling

- The `SCRY_FORMAT_CHECK` and `SCRY_TIDY_LIBCXX` script environment variables
  and the `SCRY_FUZZ_RUNS` CMake option are gone. `scripts/ci-local.sh` no
  longer runs the format check (`scripts/preflight.sh` and the documentation
  leg do). To analyze against libc++, pass `-DSCRY_CLANG_TOOLING_LIBCXX=ON` to
  `scripts/ci-tidy.sh`. `ctest` on the `fuzz` preset replays the checked-in
  corpus once instead of running a fixed number of iterations.
  ([#107](https://github.com/crybo-rybo/scry/pull/107))
- Scheduled CI retries its toolchain installs up to three times.
  ([#111](https://github.com/crybo-rybo/scry/pull/111))

## Upgrade

Update FetchContent pins to `v0.5.0` or request
`find_package(scry 0.5.0 CONFIG REQUIRED)`. The generated `<scry/version.hpp>`
reports `0.5.0`.

**If a test calls `scry::testing::json_string`.** Replace it with
`scry::escape_json_string`; the output is identical.

**If a test calls `anthropic_tool_block_events` or `openai_tool_call_entry`.**
Build the complete body with `anthropic_tool_stream` or `openai_tool_stream`
instead.

**Everyone else.** Rebuild; no source changes are needed. Provider wire formats
are unchanged except for the optional `seed` field and correctly escaped control
characters.

## Validation

Every change in this release landed through a pull request gated by hosted CI
on GCC 16 for Linux and macOS: the core gate (lizard, the `ci` build with
warnings as errors, the complete `ctest` suite, a staged install, and the
installed-package consumer), ASan with UBSan, TSan, the clang-tooling build and
clang-tidy leg, the fuzz corpus replay, and the Doxygen API site with the pinned
clang-format 18 check. Bug fixes landed with a regression test first, and the
new public field landed with `static_assert`s in `tests/public_api_contract.cpp`
and a compiling example.

Scry remains pre-1.0: API, ABI, and persisted conversation formats may change
between releases.
